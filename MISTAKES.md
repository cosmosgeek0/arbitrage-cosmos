## THE 19 WALLS — ranked by the days each one burned

**1\. PUTTING WORK IN FRONT OF THE GOAL.**
"First we need..." lists breed work; the goal day never comes. Ate 30 days.
The tell: "first," "before we can," "prerequisite."
The rule: the goal runs today with what exists. Phase order is law —
SELECT → COMPOSE → VERIFY → DEPLOY → FINAL RELEVANCE → CLEAN UP — and a
later\-phase concern can never create current\-phase work.

**2\. BUILDING MACHINERY INSTEAD OF DOING THE ACTION.**
Helper scripts, wrappers, verifiers, prompt\-review loops, command
rewriting. Nine hours once produced 11 product lines this way.
The tell: creating any new file or rewriting any prompt when a command
was expected.
The rule: action orders run existing scripts only. A new file before the
action \= already failed; stop.

**3\. TREATING DEFECTS AS BLOCKERS.**
The product has 100 defects and will never be perfect. Holding a deploy
or a finish for a defect outside the order is the perfection disease.
The tell: "but I noticed..."
The rule: only the order's own named blockers can block (for a deploy:
it failed, wrong identity serves, site unreachable, cockpit gone).
Everything else \= one report line.

**4\. INVENTING TESTS TO FEEL SAFE.**
\~413,000 test lines could not move ten dollars. Once, 183 of 194 added
lines were tests dressed as progress.
The tell: test files growing while the ordered thing is untouched.
The rule: no new tests unless the order literally says "write a test."
Test lines never count as product progress.

**5\. CHERRY\-PICKING HISTORY INSTEAD OF TAKING THE BEST WHOLE STATE.**
Piece\-by\-piece reconstruction → conflicts → "fixing" → inventing →
destruction. Two campaigns died here.
The tell: conflict resolution turning into rewriting.
The rule: adopt the best intact whole state; a donor contributes one
clearly absent, hard\-to\-recreate behavior at most. Never a whole page
"because some of it looks useful."

**6\. TOUCHING WHAT THE ORDER DID NOT NAME.**
The site died exactly this way: an unasked "improvement" deleted a
920\-line cockpit for a 60\-line shell.
The tell: your diff contains a file the order never mentioned.
The rule: the order names the files. Anything else in the diff — revert
yourself and report.

**7\. INVENTING RULES, GATES, AND LOCKS.**

The tell: quoting a rule you cannot point to in the owner's files.

**8\. RECURSIVE COORDINATION INSTEAD OF EXECUTION.**

**9\. CLAIMING DONE WITHOUT PROOF.**

The tell: a done\-claim without the exact serving identity and the seen

**10\. MAKING THE OWNER THE VERIFIER.**

The tell: asking the owner to look at something the system can measure.
The rule: the owner supplies outcome and authority. The system supplies
evidence. Missing evidence stays UNKNOWN — it never becomes an owner

**11\. TRUSTING MEMORY AFTER COMPACTION — AND KEEPING STALE STATE.**

VERIFY after DEPLOY happened) restart finished work.
The tell: feeling sure of the plan while unable to quote the file; two

The rule: memory is the disk. One factual current row exists; historical

**19\. TREATING ANOTHER SEAT'S CLAIM AS EVIDENCE.**
One chat declared the live acceptance false; another seat obeyed, paused

facts. Another seat's assertion is a hypothesis until the controller checks
