- One canonical path may create exchange mutations.
- Models never call Binance.
- Strategy never bypasses Capital or deterministic Risk.

- Server-side only.

- Deterministic fixture tests have no live network or keys.
- Signed test-order validation uses explicit integration mode and redacted receipts.
- Actual live action requires a distinct owner gate after the cockpit displays the full preview.

Directive/chat text is not authorization for private credential use, signed test-order calls, AWS/IAM/Secrets/Cloudflare/DNS mutations, deploys, service restarts, operational orders or strategy tickets.

Bind authorization to authenticated operator, account/environment fingerprint, deployed SHA, config/risk version, exact action class, server preview digest, nonce and expiry. Test-order is not live-order permission; deploy is not restart permission; operational canary is not strategy canary.

- HTTP timeout/5xx may mean `UNKNOWN`, not failed.
- Streams are timely evidence; signed REST is reconciliation.
- A private stream connected without fresh account reconciliation is not complete truth.

## 8. Canonical state and result vocabulary

The prose below is non-normative. `packages/edge-protocol/**` at `PROTOCOL_SHA` is the sole interchange schema and defines decimals/units, time precision, identifier scope, payload bounds, expiry, idempotency, compatibility/downgrade and unknown-field behavior. Generated clients cannot carry handwritten semantic copies.

### 8.1 Exchange mutation result

Use a lossless result:

```ts
type ExchangeMutationResult =
  | {
      state: "CONFIRMED";
      exchangeIdentity: ExchangeIdentity;
      exchangeStatus: string;
      receivedAt: Instant;
    }
  | {
      state: "REJECTED_NO_EFFECT_PROVEN";
      code: string;
      message: string;
      exchangeGuaranteedNotAccepted: true;
    }
  | {
      state: "UNKNOWN";
      reason:
        | "TIMEOUT"
        | "EXCHANGE_TIMEOUT_CODE"
        | "HTTP_5XX"
        | "CONNECTION_LOSS"
        | "TRUNCATED_OR_MALFORMED_ACK"
        | "PROTOCOL_MISMATCH"
        | "AMBIGUOUS_RESPONSE";
      observedStatus?: number;
      reconciliationRequired: true;
    }
  | {
      state: "PARTIAL_MIXED";
      confirmedEffects: ExchangeEffect[];
      unknownEffects: ExchangeEffectRef[];
      reconciliationRequired: true;
    };
```

Never map `UNKNOWN` to “not sent.” `REJECTED_NO_EFFECT_PROVEN` is legal only when exchange semantics prove no effect. Retryability is decided after operation-specific idempotency and reconciliation, not from an error string. Partial batch/cancel-replace outcomes remain `PARTIAL_MIXED`.

## 10. Signed exchange kernel

Build one common kernel with product-specific adapters.

### 10.1 Signing and serialization

- canonical parameter ordering/encoding;
- supported key algorithm abstraction based on actual key type;
- official signing-vector fixtures;
- exact decimal strings;
- server time offset estimator using median/outlier rejection;
- monotonic local sequence and request IDs;
- small justified `recvWindow`;
- deterministic client order IDs;
- redaction before logs/errors;
- no secrets in exception objects.

### 10.2 Rate budgets

Track product/endpoint-specific:

- request weight;
- order count;
- response headers;
- 429/418 state;
- `Retry-After`;
- cooldown;
- circuit state;
- next safe request time.

No blind retry of mutations. Read-only retries require bounded idempotent policy.

### 10.3 Ambiguity

On timeout, connection loss or relevant 5xx:

1. persist `UNKNOWN`;
2. block duplicate send for the deterministic client order ID;
3. listen for private execution event;
4. query order/trade state after bounded delay;
5. reconcile;
6. only then decide whether a new intent is allowed.

### 10.4 Test-order validation

Support Spot and USD-M signed test-order endpoints as capability validation. A passing test order proves signature/filter/request construction, not fill logic or strategy edge.
