## 16. Log-flood and incident law

The system may produce thousands of technical events. The owner must not read them all.

Separate four layers:

```text
metrics: numeric operational state
structured logs: technical detail
ledger: durable business/authority history
incidents/notifications: compressed operator attention
```

Implement:

- event fingerprinting;
- deduplication windows;
- count aggregation;
- rate limiting/sampling for repetitive debug noise;
- never sample money mutations, risk decisions, recovery, config changes, or security events;
- causal/root-cause grouping;
- severity escalation when capital is exposed;
- bounded retention and rotation;
- redaction of secrets/private payloads;
- correlation trace links;
- top-N operator attention queue.

The dashboard shows incidents and material decisions. The Logs page shows searchable detail. The ledger remains immutable business evidence.

### Event delivery correctness

The July-11 client baseline polls a large `/api/events` window using a timestamp cursor. That pattern is not sufficient for a high-rate production event feed:

- many events can share one millisecond;
- advancing by `latestTimestamp + 1` can skip same-time events;
- large repeated payloads create browser/server load;
- raw technical events become accidental notifications;
- reconnects can create gaps or duplicates.

Replace or adapt it to a gap-free monotonic event-ID cursor and bounded pagination. Use the existing application WebSocket or a bounded SSE/read API according to current architecture. Support resume from last durable event ID, deduplicate by stable ID, expose truncation/gap state, and require explicit backfill when continuity cannot be proven.

Do not send every raw metric/log line to the browser. Produce server-side aggregates and material event projections; fetch raw detail only for an opened trace or bounded query.
